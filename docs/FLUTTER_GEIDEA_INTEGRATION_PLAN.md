# Flutter Geidea Integration Plan

## Overview

This document provides a clear, implementation-oriented plan for integrating the Flutter app with the new Geidea payment backend. The backend has been fully migrated from Stripe to Geidea, and this plan explains how the Flutter app should work with the new system.

**Important**: This is a **planning document**, not implementation code. Focus on understanding the flow and architecture first.

---

## Core Principles

### 1. Backend-First Architecture
- **Flutter is a client**: All payment logic lives on the backend
- **No payment processing in Flutter**: Flutter only orchestrates the UI flow
- **Backend is source of truth**: Payment status comes from backend, not from Geidea SDK response

### 2. merchant_reference is the Key
- Generated by backend in `prepare-payment`
- Flutter stores it locally (before checkout)
- Used for all subsequent operations (create subscription, check status)
- **Never extract from URL**: Flutter doesn't rely on returnUrl

### 3. Webhook + Polling Strategy
- **Webhook is primary**: Backend receives webhook and updates payment status
- **Polling is fallback**: Flutter polls if webhook hasn't processed yet
- **Self-healing**: Backend can verify via API if polling detects old pending status

### 4. Idempotency Everywhere
- All `create-subscription` calls are idempotent
- Same `merchant_reference` = same subscription (no duplicates)
- Safe to retry any operation

## Detailed Flow Breakdown

### Phase 1: Prepare Payment

**Endpoint**: `POST /api/v1/user/subscriptions/prepare-payment`

**Request**:
```json
{
  "plan_id": 1,
  "type": "subscription_create",  // optional
  "context": "app"                 // optional: app|web
}
```

**Response**:
```json
{
  "success": true,
  "data": {
    "merchant_reference": "diplomasi_20260131191816_uuid-here",
    "checkout_url": "https://checkout.geidea.net/...",
    "session_id": "session_123",
    "order_id": "order_456",
    "amount": 100.00,
    "currency": "SAR",
    "expires_at": "2026-01-31T20:18:16+00:00"
  }
}
```

**What Flutter Must Do**:
1. Call this endpoint when user selects a plan
2. **Immediately store `merchant_reference` locally** (SharedPreferences, GetStorage, etc.)
3. Save the `checkout_url` for opening Geidea checkout
4. Note the `expires_at` timestamp (for timeout handling)

**Key Points**:
- `merchant_reference` is generated by backend (not Flutter)
- Store it **before** opening checkout (for resume logic)
- `checkout_url` is what you'll open in Geidea SDK/WebView

---

### Phase 2: Open Geidea Checkout

**Options**:
1. **Geidea Flutter SDK** (preferred, if available)
2. **WebView** (fallback, always works)

**What Flutter Must Do**:
1. Open checkout using `checkout_url` from prepare-payment
2. User completes payment or cancels
3. **On return/close**: Don't extract anything from URL
4. Immediately proceed to Phase 3 (create-subscription)

**Important**:
- Flutter doesn't know payment result from SDK/WebView
- Backend knows the real status (via webhook)
- Always call create-subscription after checkout closes

---

### Phase 3: Create/Confirm Subscription

**Endpoint**: `POST /api/v1/user/subscriptions`

**Request**:
```json
{
  "plan_id": 1,
  "merchant_reference": "diplomasi_20260131191816_uuid-here",
  "auto_renew": true  // optional
}
```

**Response Scenarios**:

#### Scenario A: Payment Already Completed (Webhook Processed)
```json
{
  "success": true,
  "data": {
    "status": "completed",
    "subscription": {
      "id": 123,
      "plan_id": 1,
      "status": "active",
      "start_date": "2026-01-31",
      "end_date": "2026-02-28",
      ...
    },
    "message": "Subscription already created"
  }
}
```

#### Scenario B: Payment Still Pending (Webhook Not Yet Processed)
```json
{
  "success": true,
  "data": {
    "status": "pending",
    "message": "Payment is still being processed. Please check payment status."
  }
}
```

#### Scenario C: Payment Failed
```json
{
  "success": false,
  "data": {
    "status": "failed",
    "reason": "Payment declined",
    "message": "Payment failed: Payment declined"
  }
}
```

**What Flutter Must Do**:
1. Call this endpoint immediately after checkout closes
2. Check the `status` field in response:
   - **`completed`**: Show success, refresh subscription, clear stored `merchant_reference`
   - **`pending`**: Start polling (Phase 4)
   - **`failed`**: Show error, allow retry, clear stored `merchant_reference`

**Idempotency Note**:
- Safe to call multiple times with same `merchant_reference`
- Backend returns existing subscription if already created
- No duplicate subscriptions possible

---

### Phase 4: Polling (If Pending)

**Endpoint**: `GET /api/v1/user/subscriptions/payment-status?merchant_reference=...`

**Response**:
```json
{
  "success": true,
  "data": {
    "status": "pending|completed|failed|not_found",
    "updated_at": "2026-01-31T19:20:00+00:00",
    "reason": "...",           // if failed
    "subscription_id": 123      // if completed
  }
}
```

**Polling Strategy**:

**Fixed Rules** (from plan):
- **maxAttempts**: 15
- **delays**: 2s, 3s, 5s, 8s, 10s, 10s... (cap at 10s)
- **stop conditions**:
  - `status === 'completed'` → Stop, refresh subscription, show success
  - `status === 'failed'` → Stop, show error
  - `status === 'not_found'` → Stop, show error
  - `maxAttempts reached` → Stop, show "We are verifying, try again later"

**Self-Healing**:
- Backend automatically verifies via Geidea API if attempt is old (>60s) and still pending
- Flutter doesn't need to do anything special for this

**What Flutter Must Do**:
1. Start polling immediately after receiving `pending` status
2. Use exponential backoff with cap (as specified)
3. Show loading indicator during polling
4. On `completed`: Stop polling, refresh subscription, clear `merchant_reference`, show success
5. On `failed`: Stop polling, show error, clear `merchant_reference`
6. On timeout: Show message, allow manual refresh

---

### Phase 5: Resume Logic (App Restart)

**Scenario**: User kills app mid-checkout, or app crashes

**What Flutter Must Do**:
1. **On app start / PlansPage open**: Check if stored `merchant_reference` exists
2. If exists:
   - Call `GET /subscriptions/payment-status?merchant_reference=...`
   - Check response status:
     - **`pending`**: Resume polling (same strategy as Phase 4)
     - **`completed`**: Call `GET /subscriptions/current`, cleanup, show success
     - **`failed`** or **`not_found`**: Cleanup stored `merchant_reference`, show message

**Implementation Note**:
- Store `merchant_reference` in persistent storage (SharedPreferences, GetStorage)
- Check on app initialization or when PlansPage is opened
- Clear `merchant_reference` only when payment is completed, failed, or not found

## State Management Considerations (GetX)

### Recommended State Structure

```dart
// Example structure (adapt to your existing GetX setup)

class SubscriptionController extends GetxController {
  // Current subscription
  final Rx<Subscription?> currentSubscription = Rx<Subscription?>(null);
  
  // Payment flow state
  final Rx<PaymentFlowState> paymentFlowState = PaymentFlowState.idle.obs;
  final RxString? currentMerchantReference = RxString?();
  final RxInt pollingAttempts = 0.obs;
  
  // Plans
  final RxList<Plan> plans = <Plan>[].obs;
  final RxBool isLoadingPlans = false.obs;
}

enum PaymentFlowState {
  idle,           // No active payment
  preparing,     // Calling prepare-payment
  checkout,      // Geidea checkout open
  confirming,    // Calling create-subscription
  polling,       // Polling payment-status
  completed,     // Payment completed
  failed,        // Payment failed
}
```

### State Transitions

```
idle
  ↓ (user selects plan)
preparing
  ↓ (prepare-payment success)
checkout (store merchant_reference)
  ↓ (checkout closes)
confirming
  ↓
  ├─→ completed (if webhook already processed)
  └─→ polling (if webhook not yet processed)
       ↓
       ├─→ completed (polling success)
       └─→ failed (polling timeout/failure)
```

## Key Differences from Stripe

### 1. No Payment Intent / Client Secret
- **Stripe**: Flutter received `client_secret`, used Stripe SDK
- **Geidea**: Flutter receives `checkout_url`, opens in SDK/WebView

### 2. No Ephemeral Key
- **Stripe**: Used for saved cards
- **Geidea**: Tokenization handled by backend (optional, not in Flutter scope)

### 3. No Direct SDK Response Trust
- **Stripe**: Flutter could trust SDK response
- **Geidea**: Flutter **never** trusts SDK/WebView response
- **Always** check backend via `create-subscription` or `payment-status`

### 4. merchant_reference Instead of payment_intent_id
- **Stripe**: Used `payment_intent_id` to create subscription
- **Geidea**: Use `merchant_reference` for all operations

### 5. Polling is Mandatory
- **Stripe**: Webhook usually fast, polling rare
- **Geidea**: Polling is expected fallback (webhook may be delayed)

## Error Handling

### Network Errors
- Retry with exponential backoff
- Show user-friendly message
- Allow manual retry

### Payment Failed
- Show error message from backend (`reason` field)
- Allow user to retry (start from prepare-payment)
- Clear stored `merchant_reference`

### Timeout (Polling Max Attempts)
- Show: "We are verifying your payment. Please check back later."
- Provide manual refresh button
- Don't clear `merchant_reference` (for resume logic)

### Invalid merchant_reference
- If `payment-status` returns `not_found`:
  - Clear stored `merchant_reference`
  - Show error: "Payment session expired. Please try again."
  - Allow user to start new payment

## Local Storage Requirements

### What to Store
1. **merchant_reference** (String)
   - Key: `pending_payment_merchant_reference`
   - Store: When prepare-payment succeeds
   - Clear: When payment completed, failed, or not found

### What NOT to Store
- `checkout_url` (can be regenerated)
- `session_id` or `order_id` (backend handles these)
- Payment card details (never)

### Storage Implementation
- Use GetStorage, SharedPreferences, or your existing storage solution
- Ensure persistence across app restarts
- Clear on logout (if applicable)

## Testing Scenarios

### Happy Path
1. User selects plan → prepare-payment → checkout → payment succeeds → create-subscription returns completed → success

### Webhook Delay
1. User selects plan → prepare-payment → checkout → payment succeeds → create-subscription returns pending → polling → webhook processes → polling detects completed → success

### Payment Failed
1. User selects plan → prepare-payment → checkout → payment fails → create-subscription returns failed → show error

### App Killed Mid-Checkout
1. User selects plan → prepare-payment → checkout opens → app killed
2. App restarts → detect stored `merchant_reference` → check payment-status → resume polling → success

### Duplicate create-subscription Call
1. User calls create-subscription → returns pending
2. User calls create-subscription again (same merchant_reference) → returns pending (idempotent, safe)

### Polling Timeout
1. Polling reaches max attempts → show timeout message → allow manual refresh
