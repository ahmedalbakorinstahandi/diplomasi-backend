# توافق نظام السيناريوهات مع نماذج المحتوى (حلقة / شاشة / مسارات)

## ملخص سريع

| المطلوب في النموذج | هل النظام يخدمه؟ | التفاصيل |
|---------------------|-------------------|----------|
| الحلقة (1، 2، 3...) | ✅ نعم | الحلقة = **Scenario** (سيناريو واحد لكل حلقة) |
| الشاشة (1، 2، 3...) | ✅ نعم | الشاشة = **ScenarioQuestion** |
| اختيارات (أ)، (ب)، (ج) مع "انتقل للشاشة X" | ✅ نعم | **ScenarioQuestionOption** مع `next_question_id` |
| نهاية السيناريو (انتهى السيناريو) | ✅ نعم | خيار واحد بدون `next_question_id` أو مع `next_question_id = null` |
| إعادة المحاولة (العودة للشاشة 1) | ✅ نعم | خيار واحد `next_question_id = start_question` |
| **نص مختلف حسب مصدر الوصول** (إذا جاء من شاشة 2 يظهر X، من شاشة 1 يظهر Y) | ❌ **لا** | حالياً **explanation واحد فقط** لكل شاشة — يحتاج تطوير |

---

## 1) البنية الحالية في النظام

- **Level** (المستوى): يحتوي على دروس وسيناريوهات. يمكن أن تمثل كل **حلقة** كسيناريو واحد داخل مستوى (أو مستوى = حلقة).
- **Scenario** (السيناريو): عنوان الحلقة، وبداية التدفق `start_question_id`.
- **ScenarioQuestion** (سؤال/شاشة): `question_text`، `explanation`، `code` (مثلاً "1" أو "شاشة-1").
- **ScenarioQuestionOption** (خيار): `option_text`، `next_question_id` (انتقال للشاشة التالية أو نهاية).

---

## 2) ما يخدمه النظام حالياً

### 2.1 الحلقة = السيناريو
- كل حلقة في النموذج (الحلقة 1، 2، 3...) = **Scenario** واحد.
- `title` = عنوان الحلقة (مثل: "ما هو التفاوض؟ ولماذا يبدأ النجاح من أسلوبك").
- `description` = وصف اختياري للحلقة.

### 2.2 الشاشة = السؤال
- كل "الشاشة (ك)" = **ScenarioQuestion** واحد.
- `code`: يمكن أن يكون رقم الشاشة (مثلاً `"1"`, `"2"`) لسهولة المطابقة مع النموذج.
- `question_text`: النص الرئيسي الذي يظهر على الشاشة (الموقف، السؤال، التغذية الراجعة الثابتة).
- `explanation`: شرح/تغذية راجعة **واحدة فقط** تظهر بعد الوصول لهذه الشاشة (من أي مسار).
- `type`: في نموذجك كل الشاشات اختيار من متعدد → `single_choice`.

### 2.3 المسارات والانتقالات
- "انتقل للشاشة (2)" → خيار مع `next_question_id` = الـ id (أو الـ code) للشاشة 2.
- "انتهى السيناريو" → خيار واحد فقط مع `next_question_id = null` (أو بدون خيارات إضافية؛ النظام ينهي المحاولة).
- "إعادة المحاولة" → خيار واحد `next_question_id = start_question_id` للسيناريو (الشاشة 1).

### 2.4 ترتيب الشاشات
- `order_index` على السؤال والخيار يحدد ترتيب العرض في الواجهات.
- ترتيب الإدخال من العميل يمكن أن يكون: إنشاء السيناريو أولاً، ثم إنشاء الشاشات بالترقيم (1، 2، 3...) ثم ربط الخيارات بـ `next_question_id` (باستخدام id أو code حسب ما يوفره الـ API).

---

## 3) ما لا يخدمه النظام (يحتاج تطوير)

### 3.1 النص الشرطي حسب الشاشة القادم منها

في النموذج يظهر مثلاً:

- **الشاشة (3):**  
  - "إذا جاء المتدرب من الشاشة (2)، يظهر النص: محاولة جيدة..."  
  - "إذا جاء المتدرب من الشاشة (1)، يظهر النص: أحسنت! بتصرفك هذا..."

النظام الحالي لا يدعم ذلك: لكل **ScenarioQuestion** يوجد حقل واحد فقط:
- `question_text`
- `explanation`

لذا لا يمكن أن يختلف النص (أو التغذية الراجعة) حسب "من أي شاشة وصل المتدرب".

**خيارات التطوير:**

1. **جدول محتوى شرطي (موصى به)**  
   - جدول جديد، مثلاً: `scenario_question_conditional_contents`  
   - أعمدة: `scenario_question_id`, `from_question_id` (المصدر)، `content_type` (مثل `question_text` أو `explanation`)، `content` (النص).  
   - عند عرض الشاشة: إذا كان هناك سجل يطابق `from_question_id` = آخر سؤال تمت الإجابة عنه، يُعرض `content` بدلاً من النص الافتراضي (أو بجانبه حسب التصميم).

2. **حقل JSON في ScenarioQuestion**  
   - إضافة حقل مثل `conditional_explanation` (أو `conditional_content`) من نوع JSON:  
     `{ "default": "نص افتراضي", "from_2": "نص إن جاء من شاشة 2", "from_1": "نص إن جاء من شاشة 1" }`  
   - المفتاح يمكن أن يكون `from_question_id` أو `from_question_code` (مثلاً "2", "1").  
   - الـ API عند `getCurrentQuestion` أو عند إرجاع السؤال بعد `submitAnswer` يمرر `previous_question_id` أو `last_answered_question_id`؛ والواجهة (أو الـ Resource) تختار النص المناسب من الـ JSON.

3. **تكرار الشاشة (بدون تغيير في الهيكل)**  
   - إنشاء "شاشة 3 من مسار 2" و"شاشة 3 من مسار 1" كـ ScenarioQuestion منفصلتين بنفس المحتوى تقريباً، مع اختلاف `question_text` أو `explanation` فقط.  
   - المسارات تشير إلى الشاشة المناسبة (مثلاً من شاشة 2 → شاشة 3أ، من شاشة 1 → شاشة 3ب).  
   - يعمل مع النظام الحالي لكنه يسبب تكرار بيانات ويصعب الصيانة.

---

## 4) لماذا قد "تجي البيانات بشكل غريب" من العميل؟

أسباب محتملة:

1. **ترتيب الإنشاء**  
   - لربط "الشاشة 1 → انتقل للشاشة 2" يجب أن تكون الشاشة 2 موجودة مسبقاً.  
   - إذا كان العميل يرسل الشاشات بالترتيب 1، 2، 3... ثم يربط لاحقاً، فالمشكلة قد تكون: ربط بـ `id` بينما الـ id غير متوقع، أو ربط بـ `code` غير مدعوم حالياً في الـ API.

2. **عدم دعم الـ code في الربط**  
   - الـ API الحالي يستخدم `next_question_id` (رقم داخل قاعدة البيانات).  
   - إذا كان العميل يرسل "انتقل للشاشة (2)" كرقم أو كود وليس id، فيلزم إما:  
     - أن يرسل الـ Backend قائمة شاشات السيناريو (id + code) ليعرف العميل أي id يوضع في `next_question_id`،  
     - أو أن يضاف دعم في الـ API لقبول `next_question_code` ثم تحويله إلى `next_question_id` عند الحفظ.

3. **النص الشرطي**  
   - إذا كان العميل يرسل نصوصاً مختلفة لنفس الشاشة حسب المصدر، والنظام يقبل حقل واحد فقط، فسيُخزّن نص واحد فقط (أو يُرفض جزء من البيانات)، فيبدو أن "البيانات تجي غريبة".

## 5) توصيات عملية

### قصيرة المدى (بدون تغيير قاعدة البيانات)
- استخدام **حلقة = Scenario**، **شاشة = ScenarioQuestion**، **انتقال = next_question_id** كما هي.
- للنص الشرطي: إما دمج النصوص في نص واحد (مثلاً: "محاولة جيدة... أو أحسنت! حسب المسار..." كجملة واحدة)، أو استخدام **تكرار الشاشة** (شاشتان منفصلتان للمسارين) حتى يكون للنظام الحالي تغطية كاملة.

### متوسطة المدى (تطوير يخدم النموذج بالكامل)
1. إضافة دعم **المحتوى الشرطي** (جدول أو حقل JSON كما في القسم 3.1).  
2. (اختياري) دعم **ربط بالـ code** عند إنشاء/تحديث الخيارات: قبول `next_question_code` وتحويله إلى `next_question_id` داخلياً.  
3. توثيق تنسيق الطلبات من العميل (مثلاً: حلقة → شاشات مرقمة → خيارات مع "انتقل إلى شاشة ك" أو "انتهى" أو "إعادة المحاولة") وتوضيح أن النص الشرطي يحتاج الحقول الجديدة أو التكرار.

### بخصوص "الترتيب المعين"
- إذا كان المقصود ترتيب عرض الحلقات: فهو يتحقق عبر `order_index` على الـ Scenario و/أو الـ Level.  
- إذا كان المقصود ترتيب الشاشات داخل الحلقة: فهو عبر `order_index` على الـ ScenarioQuestion.  
- إذا كان العميل يرسل البيانات بترتيب مختلف (مثلاً كل الشاشات ثم كل الربطات)، فيفضل توحيد تنسيق الطلب (مثلاً: إنشاء شاشات أولاً، ثم طلب تحديث لربط الخيارات بـ next_question_id أو next_question_code).

---

## 6) خلاصة

- **نعم، نظامك يخدم معظم النموذج**: الحلقة، الشاشة، الاختيارات، الانتقالات، نهاية السيناريو، وإعادة المحاولة كلها قابلة للتمثيل بالبنية الحالية.
- **نسبة التغطية**: تقريباً **85–90%**؛ النسبة المتبقية هي **النص الشرطي حسب الشاشة المصدر**.
- **لتلبية النماذج بالكامل**: يلزم إضافة آلية للمحتوى الشرطي (جدول أو JSON) وربما دعم ربط الانتقالات باستخدام `code` الشاشة لتبسيط إدخال البيانات من العميل.

إذا رغبت، يمكن تفصيل تصميم جدول `scenario_question_conditional_contents` وواجهة الـ API (مثلاً كيف يرسل العميل "نص للقادم من شاشة 2" و"نص للقادم من شاشة 1") وخطوات التعديل على الـ Backend خطوة بخطوة.
